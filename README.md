# fetch-url-gate

A check on the URL that a tool is about to fetch for a caller you do not fully trust. It decides on the address the URL names, not on the text, so `http://127.1`, `http://2130706433`, `http://0x7f000001` and the other spellings of 127.0.0.1 are denied the same way `http://127.0.0.1` is. Python standard library only; pytest to run the tests. I developed and tested it on Python 3.13.5 only.

## Why I wrote it

Cogent's post "Why an agent sandbox still needs a policy engine" (Oct 21, 2026) tests a rule on the URL a screenshot tool is about to fetch. Its Table 1 shows that a rule on the raw URL text misses the short, decimal and hex spellings of 127.0.0.1, a DNS name that resolves to it, and the cloud metadata address, and the post says a stronger rule could catch the spellings. I wrote that rule and measured it. Their text rule is not public; mine is a reconstruction of what the post describes (it denies `file:`, `localhost`, `127.0.0.1`, `[::1]` and `0.0.0.0`), so the comparison below is against my version of it.

## What it does

`check_url(url)` returns a verdict. It splits the URL the way the WHATWG URL Standard does (userinfo, backslashes, tabs and newlines, extra slashes), reads the host by that standard's rules, and allows only globally routable addresses over http or https.

- IPv4 spellings are read as addresses: dotted, short, decimal, hex, mixed, trailing dot, full-width digits and dots, percent-encoded. IPv6 literals are unwrapped when they carry an IPv4 address (mapped, 6to4, NAT64). Spellings with leading zeros are denied without being read (see below).
- Loopback, private, link-local (the metadata address among them), unspecified, multicast, reserved and site-local addresses are denied, and so are a few internal ranges that some Python releases treat as global (`192.0.0.0/24`, `168.63.129.16`).
- Names ending in `.localhost`, `.local`, `.internal`, `.lan` and a few more are denied, and so are single-label names. With a `resolver` function, every address a name resolves to is checked too.
- It denies what clients read in more than one way: leading zeros in an IPv4 part (octal or decimal), hosts that are not plain names (curl expands `{a,b}`), characters a browser deletes but Python's IDNA codec keeps, and spellings the two IDNA modes disagree on.
- Input it cannot read is denied. A seeded fuzz of 20,000 random strings and every case in `tests/test_review_findings.py` return a verdict without raising; a resolver that raises, or a value that is not a string, is denied as well.
- `verdict.fetch_url` is the URL rebuilt from the parts that were checked. Hand that to the fetcher, not the original string, so the fetcher cannot read the text differently.

## Run it

    python -m pytest
    python -m fetch_url_gate check http://2130706433/        # DENY  127.0.0.1 is loopback
    python -m fetch_url_gate check --resolve https://example.com/
    python -m fetch_url_gate eval --write                    # writes results/summary.md and results.csv

`eval` starts a small HTTP server on 127.0.0.1 and sends the URLs of the corpus that point at 127.0.0.1, 0.0.0.0 or plain `localhost` to it through Python's `urllib` and through `curl` (skipped if `curl` is not installed). The live part took 46 seconds on my machine.

## Results

From `results/summary.md`, generated by `eval --write` on Python 3.13.5, Windows 11. The corpus is built by rule in `fetch_url_gate/corpus.py`, so the hostile and benign counts do not depend on a seed. The live counts were the same in three runs; the server's port differs each time.

| | URLs | text rule | gate |
|---|---|---|---|
| hostile URLs allowed (misses) | 183 | 134 | 0 |
| benign URLs blocked | 27 | 6 | 0 |

The 183 hostile URLs are 21 spellings and 12 URL shapes for each of four addresses (loopback, the metadata address, a private address, 0.0.0.0), plus IPv6 literals, names, other schemes and 22 URLs for the cases a review of the first version found. `tests/test_review_findings.py` covers more of those cases than the corpus does. The gate looks names up in a fixed table in `eval`, not in real DNS. The 27 benign URLs are public names and addresses, plus URLs that only look risky, such as `https://127.0.0.1.example.com/` and a path that contains `localhost`. I added hostile URLs to the corpus while fixing the gate, so 183 to 0 is not a result on URLs I had not seen.

Does a real client reach the server? Of the 75 URLs sent to it, 40 pointed at 127.0.0.1 or `localhost` and 35 at 0.0.0.0:

| sent | reached by urllib | reached by curl | reached by either | of those, text rule allowed | of those, gate allowed |
|---|---|---|---|---|---|
| 75 | 9 | 29 | 30 | 15 | 0 |

None of the 35 URLs aimed at 0.0.0.0 reached the server. `urllib` reached few of the legacy spellings because on this machine `socket.getaddrinfo` raises for them (it does for `127.1`, decimal, hex and octal forms; `socket.inet_aton` accepts them). `curl` parses them itself and reached 29; the curl build is printed in `results/summary.md`. For example, curl reached the server through `127.1`, `2130706433` and `0x7f000001`, which the text rule allows and the gate denies. Per-family counts are in `results/summary.md`.

`curl` also reached the server with `127.0.0.1` followed by U+E0100 or U+2064, invisible code points that it deletes and that Python's IDNA codec keeps. The text rule happens to catch those two, because the literal `127.0.0.1` is still in the string, but the first version of this gate did not. The same trick on the metadata address or a private address has no literal to catch, and I could not send those to a server here.

## What this does not show

- The two clients are `urllib` and `curl` on one Windows 11 machine. I did not run a browser, Go, Java or Node. The gate follows the standard that browsers follow, but that is not tested here, and I did not run the standard's own test data.
- The server listens on IPv4 only. curl reached `[::ffff:127.0.0.1]` and the other mapped forms; `[::1]`, 6to4 and NAT64 were not reached. The metadata address and private ranges were not reached live; they are checked by parsing only.
- Names are judged by their text, or by a fixed table in `eval`. Real DNS answers that change between the check and the fetch (rebinding) and redirects after the fetch starts are not covered. The gate checks one URL; it cannot see what the fetcher does next.
- Host handling uses Python's IDNA2003 codec plus the deletions and denials above, not a current UTS46 library. Some valid right-to-left names, and names with `ß`, `ς` or a joiner, are denied. A production check should use a UTS46 implementation.
- The gate is stricter than the standard in places (leading zeros, plain names only, reserved name suffixes). The benign set is 27 URLs, so the false-positive count says little about real traffic.
- The corpus and the text rule are mine. The numbers say nothing about Cogent's rule or its product.
